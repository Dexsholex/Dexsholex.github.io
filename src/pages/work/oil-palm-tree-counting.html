Counting {{ palm_palms }} oil palms from aerial imagery

A commercial oil palm plantation needed a tree-by-tree inventory of its estate. I built a pipeline that finds each palm crown in aerial imagery and turns it into a mapped, countable point.

The question

How many palms does the plantation have, and where is each one? On an estate this size, manual counts are slow and they don't produce a map. The deliverable here is one mapped point per palm, block by block, that the plantation can query and check.

How it works

  1. ImageryAn RGB orthomosaic for each block
  2. Tiles1280-pixel chips with 256 pixels of overlap
  3. DetectionA YOLOv8 model with one class: oil palm
  4. MergeTile results joined and duplicates removed
  5. InventoryOne point per palm, in GeoPackage and CSV

The training data is a small, hand-annotated set of crowns taken from a stratified sample of tiles, chosen so that weed-only, palm-only and mixed scenes are all covered. Training, validation and test sets were split by spatial sector rather than by random tile, so the test score reflects ground the model had not seen.

Improving the model in production

As blocks came in, two failure patterns showed up: dense mature canopy, where neighbouring crowns run together, and young palms that are small and easy to miss. I re-annotated examples of both and retrained. The current model is the result of {{ palm_iterations }} training iterations, each compared against the same held-out test set.

Making the count add up

Blocks were delivered one at a time, and many of them overlapped. A check of every pair found {{ palm_overlap_hectares }} ha of shared coverage across {{ palm_overlap_pairs }} block pairs. Adding up each block's count on its own would have counted the palms in those zones two or three times.

I resolved it with one fixed rule: shared ground belongs to the block delivered first, and later blocks drop their detections inside that overlap. Every hectare is counted once.

Where elevation data was available ({{ palm_chm_blocks }} of {{ palm_blocks }} blocks), a canopy-height check flags detections that are implausibly short and probably not palms. It flags them for review; it does not delete them.

What it doesn't claim

  • Overlaps were resolved with each block's rectangular extent, not surveyed property boundaries. Block totals could shift if true boundaries are applied. The plantation total should not change much, because the overlap is real imagery overlap.
  • A few blocks keep only a thin sliver of ground after the overlap rule, so their palms-per-hectare figure looks very low. Those figures need a field check before anyone quotes them.
  • The figures above are detections. The workflow includes a counting-accuracy check against a manually counted area, and I'll add that result to the summary once it's published.

What the plantation received

  • A GeoPackage per block with two layers: crown outlines, and one point per palm with an ID, confidence score and crown area.
  • A plantation-wide master inventory that combines every block.
  • A runbook for processing new blocks without retraining, unless a new failure pattern appears.
